MISE EN PLACE (une seule fois, ~5 minutes)
1. Créez un compte gratuit sur github.com, puis : « + » > New repository > nom : canaris > Public > Create.
2. « uploading an existing file » : glissez TOUT le contenu de ce dossier, y compris le dossier .github
   (si le dossier caché pose problème : Add file > Create new file > nom « .github/workflows/update.yml » et collez le contenu).
   Cliquez Commit changes.
3. Settings > Actions > General > Workflow permissions > « Read and write permissions » > Save.
4. Onglet Actions > « Mise à jour des cours » > Run workflow (génère data.js la première fois).
5. Settings > Pages > Source : « Deploy from a branch », branche main, dossier / (root) > Save.
   Après 1-2 minutes, votre page est à l'adresse : https://VOTRE-PSEUDO.github.io/canaris/

MISE À JOUR DE LA PAGE : remplacez index.html, assets_v3.json et fetch_data.py sur GitHub (Add file > Upload files).
La modification de assets_v3.json relance automatiquement la mise à jour des cours.

USAGE QUOTIDIEN : ouvrez l'adresse (mettez-la en favori). Les cours sont mis à jour automatiquement en semaine.
Réglages dans assets_v3.json : "bucket" (actifs doublons : un seul retenu), "cap" (plafond de poids, ex. 0.10 = 10 %).

CLASSES D'ACTIFS (assets_v3.json)
- chaque actif a un champ "class" ; une seule position est achetée par classe (le meilleur actif BUY de la classe).
- "classes" donne le libellé affiché ; "displayTop" (défaut 10) fixe le nombre de classes affichées ET achetables.
- pour ajouter un actif : ajoutez-le dans "offensive" (id, ticker Yahoo, name, currency EUR/USD, class). Les ETF américains : "us": true.
- si un ticker n'existe pas sur Yahoo, l'étape « Run python fetch_data.py » affiche « ECHEC <ticker> » : l'actif est alors exclu du modèle ; on peut lister des tickers de secours dans "alt".

CATÉGORIES (assets_v3.json, champ "categories")
- chaque actif a une "category" ; chaque catégorie a un "cap" (part maximale de la part investie, catégorie ENTIÈRE) : 0.10 = 10 %, 1 = sans plafond.
- seuls les 10 actifs les mieux notés sont affichés ET éligibles à l'achat ("displayTop").
- chaque catégorie pèse proportionnellement au score de son meilleur actif BUY ; un seul actif par classe.

CANARIS
- calcul dans la devise de cotation (pas de conversion EUR), sur cours de clôture (séance en cours exclue).
- "canaryBand" (défaut 0) : bande morte pour limiter les bascules vert/rouge près de zéro (ex. 3 = on ne change d'état que si le score lissé dépasse ±3).

RÈGLES DE RÉPARTITION (assets_v3.json, bloc "regles")
- les parts sont en % du budget d'achat ; les canaris fixent seuls la part investie (100 / 50 / 0 % du versement), le reste est du cash.
- cœur : meilleur actif BUY de "ACT_DEV" (SP500 / CW8). Paliers de score -> part : >=90 : 70 %, >=80 : 60 %, >=70 : 40 %.
- compléments : or, matières premières, bitcoin (un actif BUY par catégorie) : >=90 : 15 %, >=80 : 10 %, >=70 : 5 % ; bitcoin 10 % max ; total 30 % max.
- secondaires (actions, mat. premières et or secondaires) : BUY et score >=80 ; un 2e actif seulement si son score >=90 ; budget max 5 % (principales fortes) / 10 % (moyennes) / 20 % (faibles) ; un seul actif par famille (EM, énergie, mineurs) ; MAGS exclu si le cœur est SP500/CW8.
- reliquat : reporté sur le cœur s'il est BUY ; sinon réparti entre les actifs retenus dans la limite des plafonds, le reste en cash.

MODULE « GÉRER LES ACTIFS » (fin de page)
- liste déroulante + bouton Supprimer ; formulaire d'ajout (ticker Yahoo, identifiant, nom, devise, catégorie, classe).
- chaque modification télécharge un fichier assets_v3.json modifié (nom exact à conserver). Aucun jeton GitHub n'est nécessaire.
- pour valider : GitHub > votre dépôt > Add file > Upload files > glisser assets_v3.json > Commit changes. La mise à jour des cours démarre seule.
- plusieurs modifications à la suite s'accumulent : le dernier fichier téléchargé contient tout. « Annuler les modifications en attente » recharge la liste d'origine.

EN CAS DE PROBLÈME DE COURS
- data.js et data.json sont régénérés par le workflow « Mise à jour des cours » (onglet Actions › Run workflow). Si vous les supprimez, lancez-le une fois : les 2 ans d'historique sont retéléchargés depuis Yahoo, rien n'est perdu.
- le script s'arrête après environ 9 minutes ou si Yahoo bloque l'adresse du serveur GitHub ; il enregistre alors ce qu'il a obtenu et le passage suivant (5 par jour ouvré) reprend par les actifs manquants.
- le journal de l'étape « Récupérer les cours » liste les actifs sans cours (« Sans cours pour l'instant »).
- un nouveau lancement annule le passage encore en cours (plus de file d'attente de passages).

VÉRIFIER QUE LES MISES À JOUR SE FONT
- un passage vert dans l'onglet Actions ne prouve pas que des cours ont été enregistrés : ouvrez le passage et lisez « Summary » (nombre d'actifs avec cours, actifs manquants, raison d'un arrêt anticipé).
- la preuve : un commit « Cours du AAAA-MM-JJ HH:MM » (utilisateur cours-bot) apparaît dans le dépôt. Sans commit récent, la page garde d'anciens cours.
- la page affiche « ⚠ cours anciens » en rouge si les cours ont plus de 4 jours.
- durée normale d'un passage : 2 à 9 minutes. Un passage de 12 minutes pile signifie que le script a été interrompu par le délai maximal (ancienne version de fetch_data.py).
